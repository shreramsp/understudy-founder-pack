# D03 · Execution orchestration

```mermaid
sequenceDiagram
  participant T as PSA ticket
  participant M as Skill matcher
  participant P as Policy engine
  participant X as Executor
  participant I as Client tenant (IdP/admin plane)
  participant H as Human

  T->>M: ticket context + environment id
  M->>M: match procedure shape + tenant variants
  M-->>H: surface skill, deviations, run option
  H->>P: run (gated)
  P->>P: classify each step: read / reversible / destructive
  P->>X: read steps — no approval
  X->>I: execute reads (agent principal)
  I-->>X: state
  P-->>H: reversible step — one-line effect, approve?
  H->>P: approve
  P->>X: execute, undo path recorded first
  X->>I: mutate (agent principal)
  X->>X: verify goal criterion
  alt criterion passes
    X-->>T: resolution note + verification result
  else precondition unmet or criterion fails
    X-->>H: escalate with full trace
  end
```

**What a reviewer should notice.** The undo path is recorded **before** the mutation, not derived after it — that ordering is what made the 14:20 incident a 40-second recovery. Every action reaches the client tenant under the agent's own principal, never a shared admin account, so the client's audit log attributes it without our help. Note what the diagram does *not* contain: any path from matcher to executor that bypasses the policy engine.
